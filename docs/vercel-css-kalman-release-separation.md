# CSS and Kalman Vercel deployment separation (2026-10-30)

## Goal
The existing CSS Sales Workspace and Kalman Triple Barrier Vercel projects share
`kimtk94/Codex`. Without deploy skipping, each push creates deployments for
both projects and burns the Hobby team's 100-deployment/24h quota.

## Project isolation
- CSS root: `apps/css-sales-workspace` (existing node package, private data stays server-side).
- Kalman Triple Barrier root: `research/kalman_triple_barrier/web` (static HTML, no server-side secrets).
- The repository root `package.json` declares both apps as distinct npm
  workspaces. Non-app directories are *also* private workspaces so source
  changes in `automation/**`, `.github/**`, `docs/**`, etc. do not
  incorrectly count as global monorepo changes.
- A root `package-lock.json` is generated by npm on GitHub Actions, retaining
  the legitimate CSS dependency tree and workspace mapping.
- Vercel: enable `enableAffectedProjectsDeployments` for **both** projects.
  This is different from `commandForIgnoringBuildStep`, which still consumes
  deployment slots.

## Boundaries and verification
- An update to the CSS app must affect only CSS, not Kalman.
- An update to the Kalman static web app must affect only Kalman, not CSS.
- A change in a private source-only workspace must not deploy either site.
- Root `package.json`, root lockfile and other intentionally-global root
  changes may still deploy multiple apps. Keep these rare.
- Existing Production domains, secret variables, access protection and
  Git settings stay unchanged.
- Verify deployments for two independent commits when account quota allows;
  PR offline tests alone do not prove Vercel-side event skips.
- Do not deploy just to probe quota, and do not disable authentication.

Documentation: https://vercel.com/docs/monorepos#skipping-unaffected-projects
